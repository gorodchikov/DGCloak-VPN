# Backlog — отложенные задачи

## 1. Firewalld-бэкенд: полноценная верификация NAT/forward

**Статус:** отложено. **Приоритет:** низкий (на поддерживаемых дистрах
Ubuntu 20–26 / Debian 11–13 firewalld нет из коробки).

Текущее состояние: `_step_nat` для `fw == "firewalld"` делает только
`firewall-cmd --permanent --add-masquerade --zone=public`, а пост-проверка
(`masq 10.8.0.0/24` + forward-правила `tun0`) для firewalld сознательно
пропущена — её проверки на iptables/nft на этом бэкенде давали бы ложный
`warn`.

Что нужно при реализации:
- проверять `firewall-cmd --query-masquerade --zone=public`;
- проверять форвардинг между зонами: на firewalld ≥ 1.0 masquerade
  не открывает forward — нужен `--add-forward` на интерфейсах или
  policy-объект (`--new-policy`, `--add-ingress-zone`, `--add-egress-zone`);
- в `probe.sh` добавить firewalld-ветку аудита (`--query-masquerade` +
  наличие forward-policy для tun0), иначе аудит будет врать в обе стороны.

## 2. Предупреждение: сервер управляется через свой же VPN-туннель

**Статус:** отложено.

Живой кейс (Stockholm): юзер был подключён к Amnezia, терминированной на
том же хосте, который деплоился/ребутился. SSH-сессия шла через туннель →
при остановке VPN обрыв `Software caused connection abort` в середине
деплоя.

Идея: админка и клиент (`cloak_ovpn.py`) живут в одном `%APPDATA%\DGCloak`.
Перед операциями с ребутом/перезапуском сети (Deploy all, purge, reboot)
проверять: активное VPN-подключение клиента терминируется на том же хосте,
что редактируемый сервер (совпадение server IP/host профиля с адресом
сервера)? Если да — предупреждение «вы управляете сервером через его же
туннель; SSH оборвётся». Источники данных: `VPN\data.json` (`last_profile`),
активный профиль, `pids.json` (процессы живы), remote-адрес профиля.

## 3. Добивать дочерние plink/pscp/ssh при выходе админки

**Статус:** отложено.

Живой кейс: админку закрыли во время зависшей SSH-операции (London,
провайдер убил сессию) → `plink.exe` остался сиротой, висел на мёртвой
сессии и держал рабочую директорию `dist\DGCloakAdmin` — следующая сборка
не могла перенести exe в `dist\`.

Что нужно:
- реестр PID своих дочерних процессов (plink/pscp/ssh/scp — каждый
  `_try`/`run_stream` регистрирует PID, снимает по завершении);
- на выходе (крестик/выход) `taskkill /PID … /F` по списку, с проверкой
  имени exe (защита от переиспользования PID) — аналог `pids.json`
  в клиенте (`cloak_ovpn.py`);
- опционально: сохранять список в `Admin\pids.json`, чтобы добивать сирот
  даже после аварийного завершения админки (как клиент).
