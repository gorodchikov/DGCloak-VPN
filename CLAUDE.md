# DGCloak VPN — контекст проекта для ИИ-агента

Windows-клиент для связки **OpenVPN поверх Cloak**: сначала запускается локальный прокси `ck-client.exe` (Cloak),
затем консольный `openvpn.exe`, который подключается не к серверу напрямую, а к локальному порту Cloak.
Окно на tkinter, значок в системном трее, несколько профилей, статус из management-интерфейса OpenVPN.

Язык проекта: **русский** (интерфейс, комментарии, сообщения лога). Пользователь русскоязычный и общается по-русски.

> Этот документ описывает код на момент создания репозитория. **Источник истины — код**. Если документ расходится с кодом, верьте коду и поправьте документ.

## Предыстория (зачем это всё)

Серверы OpenVPN over Cloak раньше настраивались через Amnezia: в её 5-й версии OpenVPN убрали, в старой версии
работает плохо, управления пользователями нет. Цель проекта из двух частей:
1. **Windows-клиент** — этот код, работает и используется.
2. **Серверное management-приложение** — настройка серверов по SSH (см. раздел «Планы»), пока не начато.

Важно: изначально клиент пытались сделать поверх OpenVPN Connect, но у него нет CLI-команд подключения/отключения
и статуса, поэтому перешли на консольный `openvpn.exe` (community-версия) с management-интерфейсом.

## Архитектура клиента (`cloak_ovpn.py`)

### Данные и файлы на диске
- Общая папка `%APPDATA%\DGCloak\`: `bin\` — внешние зависимости обеих программ (ck-client, plink/pscp);
  `VPN\` — данные клиента; `Admin\` — данные админки. При первом запуске новой версии старые
  `%APPDATA%\DGCloakVPN` / `%APPDATA%\DGCloakAdmin` переносятся автоматически (`migrate_dirs`),
  пути в `data.json` переписываются, ck-client переезжает в общий `bin\`.
- Папка данных клиента: `%APPDATA%\DGCloak\VPN\`
  - `data.json` — настройки и профили (только пути и параметры, **секретов нет**; ключи — в `.ovpn`/конфиге Cloak, копии которых лежат в `profiles\`).
  - `last.log` — лог текущего запуска; при старте переименовывается в `prev.log` (ротация: текущий + предыдущий). Пишется напрямую из рабочих потоков, поэтому доступен даже при зависании окна.
  - `runtime.ovpn` — копия пользовательского `.ovpn`, в которой все строки `remote` заменены на `remote 127.0.0.1 <port> <tcp-client|udp>` (порт из профиля). OpenVPN запускается с этой копией — править `.ovpn` вручную не нужно.
  - `profiles\<имя>\` — при добавлении/изменении профиля его файлы (`ck_config`, `.ovpn` и внешние ключи, на которые .ovpn ссылается — `ca`/`cert`/`key`/`tls-auth` и т.п.) копируются сюда (`import_profile_files`), в data.json пишутся новые пути; исходники пользователь может удалить. При удалении/переименовании профиля папка подчищается.
  - `pids.json` — PID запущенных нами `ck-client`/`openvpn`. Перед подключением сохранённые PID добиваются `taskkill` (с проверкой имени exe — защита от переиспользования PID), так что зависший процесс после аварийного завершения не мешает переподключению. Чужие процессы с теми же именами по-прежнему вызывают отказ с предупреждением.
- Схема `data.json`:
```json
{
  "ck_client": "C:\\Tools\\Cloak\\ck-client-windows-amd64.exe",
  "openvpn_exe": "C:\\Program Files\\OpenVPN\\bin\\openvpn.exe",
  "last_profile": "Stockholm",
  "profiles": [
    {"name": "Stockholm", "ck_config": "D:\\...\\stockholm.json", "ovpn": "D:\\...\\stockholm.ovpn",
     "port": 1984, "server": "", "server_port": "", "bypass_ip": "",
     "udp": false, "full_tunnel": true}
  ],
  "language": "ru"
}
```
  Поле `imported` в старых профилях — устаревшее, игнорируется. Последний успешно подключённый профиль сохраняется в `last_profile` и выбирается при старте.

### Запуск процессов (поток подключения, `App._connect`)
Выполняется в рабочем потоке (`_run` → `threading.Thread`). Все подпроцессы запускаются с `CREATE_NO_WINDOW`,
`stdin=DEVNULL`; stdout и stderr объединены в PIPE и читаются отдельным потоком (`_pump`) в лог.

0. **Предполётные проверки:** `repair_loopback()` (добавляет системный маршрут `127.0.0.1/32`, если его нет; см. ниже),
   `loopback_ok()` (локальный TCP на 127.0.0.1 работает), добивание своих зависших процессов по `pids.json`,
   `find_procs()` (чужие `ck-client`/`openvpn` — отказ с PID), проверка, что локальный порт Cloak свободен.
1. **Cloak:** `ck-client.exe -c <ck_config> -l <port> [-s <server>] [-p <server_port>] [-u]`.
   Локальный порт задаётся флагом `-l` (в json-конфиге Cloak его **нет**). Затем ждём до 15 с, пока порт начнёт принимать TCP (`probe()`);
   в UDP-режиме порт проверить нельзя, просто пауза 3 с.
2. **OpenVPN:**
```
   openvpn.exe --config <APP_DIR\runtime.ovpn> --cd <папка исходного ovpn> --management 127.0.0.1 <случайный свободный порт>
               --disable-dco [--route <bypass_ip> 255.255.255.255 net_gateway]
               [--redirect-gateway local def1] [--verb 4]
   `runtime.ovpn` создаётся функцией `_runtime_ovpn`: remote из профиля (`port`), proto по галочке `udp`.
```
3. **Статус через management:** поток `_mgmt_loop` подключается к management-порту, шлёт `state on all`, разбирает строки состояний
   регулярным выражением `STATE_RE`; на `CONNECTED` выставляется `self.up` (Event) — основной поток подключения ждёт его до 60 с
   (с «пульсом» в лог каждые 5 с). Состояния → русский текст/цвет — словарь `STATES`.
4. После успеха: `self.active = профиль`, сохранение `last_profile`, запуск `_monitor` (раз в 2 с проверяет, живы ли процессы Cloak и OpenVPN;
   при падении статус красный). Если в выводе OpenVPN были «route add command failed» (`route_failed`), показывается предупреждение о правах администратора.

### Отключение (`_disconnect` → `_stop_all`)
Остановка монитора → `_stop_vpn` (команда `signal SIGTERM` через management для штатной очистки маршрутов; ждём 10 с, затем `terminate`/`kill`) →
`_stop_ck` (terminate/kill) → `_check_loopback` + `repair_loopback`. Жёсткое убийство OpenVPN оставляет мусорные маршруты — избегать.

### Потоки и интерфейс (важные правила)
- **Из рабочих потоков нельзя трогать tkinter напрямую.** Обновление интерфейса только через `self.ui(fn)` — очередь, которую разбирает `_drain` в главном потоке каждые 100 мс (устойчива к исключениям в отдельных колбэках).
- Лог: `self.say(msg)` пишет в `last.log` сразу и в виджет через очередь.
- Колбэки pystray выполняются в потоке трея → всегда оборачивать в `self.ui(...)`. Из потока трея читаются только простые атрибуты (`active`, `busy`, `cur_name`, `data["profiles"]`), не виджеты.
- Необработанные исключения в потоках и tk-колбэках пишутся в лог (`threading.excepthook`, `report_callback_exception`) — в exe без консоли иначе они невидимы.
- Окно фиксированного размера (`resizable(False, False)`); кнопка «Дополнительно» раскрывает лог, «Копировать лог»/«Очистить лог», «Пути к Cloak и OpenVPN…», галочку «Отладочный лог OpenVPN» (`--verb 4`). При ошибке панель раскрывается сама.
- Диалог профиля (`ProfileDialog`): видны название и два пути к файлам; редкие поля (порт, сервер, IP-обход, UDP, full_tunnel) — под раскрывашкой «Дополнительно ▾». При редактировании профиля с нестандартными скрытыми полями секция открыта сразу.
- Язык интерфейса: `data.json["language"]` = `ru`|`en`, переключение — комбобокс «Язык» внизу основного окна справа. Переводы — словарь `STRINGS_EN` (ключ — русская строка), `self.t(ru, **kw)`; лог и лог-файл остаются по-русски. Пояснение про язык старых записей лога — тултип на «Язык:»/комбобоксе (класс `Tooltip`), диалога при смене языка нет.
- Крестик и «свернуть» прячут окно в трей (`_hide_to_tray`). Выход: пункт «Отключить VPN и выйти из программы» в меню трея или кнопка «Выход» в окне (с подтверждением при активном VPN).
- Меню трея динамическое (`_tray_items`, пересобирается через `update_menu()` при смене статуса/профиля): «Открыть»; при отключённом — «Подключить «name»» + «Подключить ▸ профили кроме выбранного»; при активном — «Отключить «name»» отдельным пунктом + «Отключить «name» и подключить ▸» (подменю: профили кроме подключённого, выбор = переключение; показывается, если есть другие профили); «Отключить VPN и выйти из программы». Цвет плаща в трее = статус.
- Без `pystray`/`Pillow` программа работает без трея (`HAS_TRAY = False`), крестик тогда закрывает программу.

## Сетевая логика

```
openvpn.exe ──TCP──► 127.0.0.1:<порт Cloak> ──ck-client.exe──► (TLS-подобный трафик, TCP/443) ──► ck-server ──► OpenVPN-сервер
   (remote 127.0.0.1 <порт>)        локальный прокси                  маскируется под HTTPS
```
- Строки `remote` в `.ovpn` игнорируются: `_runtime_ovpn` подставляет `remote 127.0.0.1 <port> <proto>` из профиля (порт = `-l` Cloak, proto по галочке UDP). Порт в настройках профиля — единственное место, где он задаётся.
- Cloak слушает только `127.0.0.1`; OpenVPN думает, что подключается к серверу, а Cloak пробрасывает трафик на реальный сервер.
- **Обход туннеля для трафика самого Cloak.** При полном туннеле (`redirect-gateway def1`) трафик ck-client к реальному серверу нельзя заворачивать в VPN (петля). Нужен маршрут до IP сервера Cloak через основной шлюз:
  в `.ovpn` (`route <IP> 255.255.255.255 net_gateway`) или полем `bypass_ip` в профиле (добавляется аргументом `--route`).
- **Флаг `local` в `--redirect-gateway local def1` критичен.** Без него OpenVPN пытается создать обходной маршрут до `remote`, то есть до `127.0.0.1`, а при выходе удаляет его — вместе с **системным маршрутом loopback**.
  Следствие в живой системе: после отключения 127.0.0.1 переставал отвечать, Cloak «не поднимал порт», ломались другие программы (v2rayN), помогала только перезагрузка.
  Страховка поверх флага: `repair_loopback()` (`route ADD 127.0.0.1 MASK 255.255.255.255 0.0.0.0 IF 1` до и после сеанса; код возврата 0 = маршрута не было и он восстановлен).
- `--disable-dco`: DCO-драйвер плохо дружит с локальным прокси; нужен OpenVPN ≥ 2.6. На практике используется драйвер TAP-Windows6.
- Подключение занимает ≈6 с: туннель поднимается за секунду, маршруты добавляются через 5 с (штатный `route-delay`).
- Проверочное подключение программы к порту Cloak создаёт одноразовую сессию Cloak; строки Cloak `Failed to read first packet from proxy client: EOF` в логе безвредны.
- Management-порт OpenVPN слушает только localhost, **без пароля** (OpenVPN предупреждает об этом). Известный компромисс, кандидат на улучшение.
- Запускать TUN-режим v2rayN одновременно с этим VPN нельзя (конфликт виртуальных адаптеров и маршрутов).
- Профили с `auth-user-pass` (логин/пароль) **не поддерживаются** (запрос приходит в management как `>PASSWORD:`, сейчас только пишется в лог).

## Сборка и запуск на Windows

Требования:
- Windows 10/11, Python с python.org (3.8+, лучше 3.10+; нужен tkinter).
- `ck-client.exe` (Cloak, клиент) и **OpenVPN Community** (консольный `openvpn.exe`, не OpenVPN Connect) с драйвером TAP-Windows6; проверялось на OpenVPN 2.7.7.
- **Права администратора** (создание адаптера и маршрутов). Без них OpenVPN отвечает `Access is denied` на добавление маршрутов.

Запуск из исходников (от администратора):
```bat
pip install -r requirements.txt
python cloak_ovpn.py
```
Первый запуск (`_first_run`, через ~400 мс после старта): программа ищет `openvpn.exe` (PATH, Program Files) и `ck-client.exe` (папка данных, PATH), подставляет найденное в `data.json`; чего не хватает — показывается мастер `SetupDialog`: «Установить автоматически» ставит OpenVPN через `winget install OpenVPNTechnologies.OpenVPN` (есть в Win11 и обычных Win10; на LTSC/Server может отсутствовать — тогда ручная установка) и скачивает свежий `ck-client-windows-amd64*.exe` через GitHub API `releases/latest` в `%APPDATA%\DGCloak\bin`. Пути проверяются быстрым запуском (`exe_runs`, таймаут 10 с). Если профилей нет — предлагается добавить первый. Ручная смена путей: «Дополнительно» → «Пути к Cloak и OpenVPN…».

Сборка exe:
```bat
build.bat
```
Скрипт ставит `pyinstaller pystray pillow`, генерирует `app.ico` (`python cloak_icon.py app.ico`) и вызывает
`PyInstaller --noconsole --onefile --uac-admin --icon app.ico --version-file version_info.txt --hidden-import pystray._win32 --name DGCloakVPN cloak_ovpn.py`.
`version_info.txt` — версионный ресурс exe (описание, версия 1.0, © 2026 Dan Gorodchikov, ru-RU/en-US).
Результат: `dist\DGCloakVPN.exe` (сам запрашивает UAC). `--onefile` иногда вызывает ложные срабатывания антивирусов — тогда собирать `--onedir`.

## Известные проблемы и допущения

- **Нет автотестов; код писался и проверялся итеративно на машине пользователя.** Автор кода (ИИ) не мог запускать Windows-часть. Среда агента, скорее всего, Linux: tkinter-окно, `route.exe`, `tasklist`, `ctypes.windll` там не работают. Чистую логику (разбор состояний, формирование аргументов, `load_data`) лучше выносить в тестируемые функции.
- **Открытая проблема:** на ряде серверов, созданных Amnezia (AWS Lightsail), через ≈20 с после `CONNECTED` приходит `Connection reset by peer`
  от локального `ck-client` и начинается реконнект (OpenVPN при этом переподключается за ≈2 с и каждый раз получает новый адрес туннеля). На других серверах всё стабильно.
  Причина не установлена (сервер, сеть до него или Cloak). Клиентской ошибкой, по имеющимся данным, не является. Сначала проверять серверную сторону и поведение на свежеразвёрнутом сервере (см. «Планы»).
- Часть защитной логики (`repair_loopback`, `STATE_RE`, `route_failed`, `state on all` вместо `--management-hold`) появилась в процессе отладки; она подтверждена логами пользователя, но пересматривайте осознанно.
- Флаги CLI Cloak (`-c -l -s -p -u`) взяты из знаний ИИ и подтверждены работой; при обновлении Cloak сверяться с `ck-client -h`.
- Нет логина/пароля, нет шифрования секретов (их в `data.json` и нет), нет автозапуска и автоподключения при старте.

## Правила разработки

- Совместимость с Python 3.8+. Зависимости минимальные (stdlib + pystray + Pillow); новые добавлять осознанно.
- Не вызывать tkinter из рабочих потоков; всё через `self.ui`.
- Новые сообщения пользователю — по-русски, в лог — через `self.say`.
- Не менять формат `data.json` без обратной совместимости (пользовательские профили лежат в `%APPDATA%\DGCloak\VPN\data.json`).
- Любые изменения запуска процессов/маршрутов осторожно: ошибки оставляют систему без рабочей сети до перезагрузки. Не убивать `openvpn.exe` жёстко без необходимости.
- Не коммитить: `data.json`, `*.ovpn`, конфиги Cloak, ключи, логи (логи содержат имена/IP серверов).

## Методология локализации (использована в админке; для клиента и новых UI)

Паттерн: **ключ — русская исходная строка**, `STRINGS_EN` — dict ru→en, фолбэк на
ключ. `self.t(ru)` — в классах, `T(ru)` — в модульных функциях (читает глобальный
`_LANG`). Форматирование: `self.t("…%s…") % args` — переводится шаблон, плейсхолдеры
сохраняются. Выбор языка — комбобокс, `data.json["language"]`, старт —
`detect_lang()` (GetUserDefaultUILanguage: ru* → ru, иначе en).

Алгоритм внедрения в файл со сплошным русским UI:

1. **AST-кодмод** (`tools/i18n_codemod.py`, запуск: `python tools/i18n_codemod.py <file.py>`)
   оборачивает все кириллические `Constant` внутри тел функций в `self.t(...)` /
   `T(...)`. Грабли, которые уже учтены в скрипте:
   - docstring'и (Expr→Constant) — пропускаются;
   - дефолты/аннотации аргументов — пропускаются (вычисляются при `def`, self нет);
   - ключи dict — пропускаются (lookup-ключи), значения — оборачиваются;
   - операнды `Compare` — пропускаются (это проверки сохранённых данных/вывода);
   - вложенные функции видят `self` через замыкание — флаг не сбрасывается;
   - строки вне функций (class-level STEPS и т.п.) — не трогаем: их надо
     оборачивать в точке использования, не при определении.
2. **Ручная доработка после кодмода** (контрольный список):
   - класс-таблицы (STEPS): переводить заголовок при рендере (`self.t(title)`);
   - dict «label-ключ → tip-текст»: значения оставить RU, переводить в точке
     показа — иначе lookup по переведённому тексту ломается;
   - `title="…"` в дефолтах `__init__`: выставить `self.t = parent.t` ДО
     `super().__init__()` (body() вызывается внутри него) и передать
     `self.t(title)`;
   - сравнения с собственными переведёнными строками (`"не удалять" in lbl`,
     `"(пустой вывод)" in msg`) — заменить на функциональную проверку
     (`_port_protected`) или проверять `self.t()`-вариант;
   - исторические записи (лог, заметки шагов) НЕ переводятся задним числом —
     проверки по их тексту должны принимать оба языка;
   - метод `_w`/`_tw` для виджетов: НЕ называть `self._w` — это внутренний
     pathname виджета tkinter, коллизия = RecursionError в repr.
3. **Живое переключение** — реестры: `self._i18n` [(widget, ru, args)] через
   `_tw(w, ru, *a)`, `self._tips` через `_tip`, `self._nb_tabs` для вкладок
   Notebook, отдельно заголовки Treeview (`_users_heads`) и динамические
   StringVar-подписи (хранить шаблон, переприменять в `_apply_lang`).
4. **Что не переводим:** вывод внешних утилит (plink/apt/openvpn/ck-client),
   значения автонимов комбобокса («Русский»/«English»), маркеры внешних
   протоколов, docstring-комментарии.
5. **Проверка:** скрипт-свёртка «все `t()`-ключи ∈ STRINGS_EN» (см. приём в
   истории: ast-обход `visit_Call` + импорт модуля), затем smoke: создать App,
   переключить язык, проверить вкладки/кнопки/заголовки + что старый лог
   не перевёлся, а новые строки — на новом языке.

Клиент (`cloak_ovpn.py`) локализован так же: `STRINGS_EN`, `self.t`, `language`
в data.json — но БЕЗ перевода лога; при доработке привести к той же модели
(лог переводится при записи, история не трогается).

## Серверная админка (`cloak_admin.py`)

Локализация: `STRINGS_EN` + `self.t(ru)`/`T(ru)` (модульные функции), выбор —
комбобокс «Язык» внизу вкладки «Развёртывание»; стартовый язык — по локали
Windows (`detect_lang`: ru* → ru, иначе en), сохраняется в `data.json["language"]`.
Смена языка — живая (`_apply_lang`: реестры `_i18n`/`_tips`/`_nb_tabs` +
заголовки таблиц). Журнал и заметки шагов переводятся при записи — история
остаётся на языке создания. Вывод внешних утилит не переводится.

Приложение-менеджер серверов (tkinter, по образу клиента): реестр серверов, аудит,
авто-развёртывание, управление юзерами, экспорт бандлов. Данные:
`%APPDATA%\DGCloak\Admin\data.json` (серверы + реестр юзеров cn↔uid), бандлы в
`bundles\<сервер>\<юзер>\`. Реализовано и проверено на живом сервере (London, AWS):

- **SSH-слой — внешние plink/pscp** (класс `SSH`): ppk нативно, пароль как опция;
  host key принимается автоматически (TOFU: сначала `-batch`, при «not cached» —
  повтор с `y` на stdin). Скрипты заливаются pscp в `/tmp/dgadm-*`, затем
  `sudo bash` (подразумевается NOPASSWD sudo или root). CRLF вычищается sed'ом.
- **Деплой** — 9 шагов (UI: большая кнопка «Развернуть всё» + отдельные шаги):
  SSH → ключевая авторизация → аудит (`detect.sh`, гейт по ОС: apt-дистры вне
  матрицы — «на свой страх») → фаервол (`fw-detect.sh` → `fw-install.sh` при
  `none`, иначе существующий бэкенд) → `sysupdate.sh` → `pkgs.sh` →
  `deploy-openvpn.sh` (PKI+server.conf+mgmt:7505) → NAT (`nat-enable.sh` /
  `deploy-net-ufw.sh` / `deploy-net-iptables.sh <ssh_ports> <ck_port>` /
  firewalld inline) → `deploy-cloak.sh` (PUB/ADMIN_UID → реестр).
- **Фаерволы**: единый фронт `fw-manage.sh` (`list`/`ports`/`allow`/`deny`) поверх
  nftables-dg (наша таблица `inet dgcloak`), ufw, firewalld, iptables-persistent,
  чужих iptables (только чтение). В `ports` firewalld-сервисы (ssh→22,
  dhcpv6-client→546) раскрываются в порты через `--info-service`.
- **Грабли скриптов (важно):**
  - `set -o pipefail` + `| grep -q` = флаки: ранний выход grep'а → SIGPIPE
    производителю → rc=141 вместо 0 (на старых nft 0.9.x почти всегда).
    Правило: в пайпе `| grep 'pat' >/dev/null`, без `-q`.
  - Порядок детекции: `iptables-persistent` (файл rules.v4) проверять РАНЬШЕ
    чужого nftables — на iptables-nft-системах его правила видны в `nft list`.
  - Порт Cloak из GUI (`v_ckport`) должен доезжать везде: `fw-install.sh $2`,
    `deploy-net-iptables.sh $2`, `deploy-cloak.sh $4` (BindAddr+проверка),
    admin-API `RemotePort`, метки в диалоге портов. В `_step_nat` после NAT —
    всегда `fw-manage.sh allow tcp <ck_port>` (бэкенд-агностично).
  - plink без консоли не отвечает на host-key prompt: парсим fingerprint из
    batch-вывода и повторяем с `-hostkey` ПЕРЕД target-аргументом.
  - OpenVPN 2.4 (Ubuntu 20.04): `openvpn --genkey --secret f` (не `secret f`),
    easy-rsa только через `--batch` (printf-stdin → SIGPIPE), в server.conf
    нужен `cd /etc/openvpn/server` для относительных путей.
  - Debian 11 в архиве: apt нужен `-o Acquire::Check-Valid-Until=false` и
    `archive.debian.org` вместо deb.debian.org.
- **Юзеры Cloak — локальный `ck-client.exe -a <AdminUID>`** (класс `CloakAPI`):
  пишет временный конфиг (`UDP:false` обязательно — с `true` API не поднимается;
  `LocalPort` — реальный свободный порт, `"0"` НЕ работает — API висит на :0);
  ждёт `API base is 127.0.0.1:PORT` в stdout; HTTP `GET/POST/DELETE /admin/users[/<uid-b64url>]`;
  клиент засыпает по idle → перезапуск на каждую пачку + рестарт при обрыве.
  UID генерируется локально: `base64(16 random bytes)`, в URL — base64url.
- **Сертификаты** — `user-cert.sh` на сервере (easyrsa gen-req/sign-req, вывод
  CA/CERT/KEY/TA маркерами `===X===` в stdout); отзыв — `sudo bash -c 'cd
  /root/openvpn-ca && revoke + gen-crl + install crl.pem'` (CA в /root — весь
  конвейер под sudo, иначе permission denied).
- **«Отключить сейчас»** — `scripts/ovpn-mgmt.py` на сервере через management
  `127.0.0.1:7505` + `mgmt.pass` (`kill <CN>`; `clients` — список онлайн).
- Серверные скрипты — в `scripts/`; параметры деплоя в GUI: домен маскировки,
  proto udp/tcp, чистка Amnezia, MSS-clamp, первый юзер.
- **«Подтянуть ключи»** — импорт управления над уже развёрнутым сервером без
  передеплоя (читает publickey.txt/adminuid.txt по SSH).

## Планы (по убыванию приоритета)

1. **Структура и качество:** разнести `cloak_ovpn.py` на модули (конфиг/профили, запуск процессов, сетевые утилиты, GUI, трей), вынести построение аргументов Cloak/OpenVPN в чистые функции и покрыть тестами; CI на GitHub Actions (`windows-latest`: `py_compile`, сборка exe).
2. **Клиент:** пароль на management-порт; поддержка `auth-user-pass`; автоподключение при старте; импорт клиентского пакета (`.ovpn` + `ckclient.json`) одной кнопкой; переключение профиля без ручного отключения.
3. **Серверное management-приложение** — реализуется, см. раздел «Серверная админка (`cloak_admin.py`)» выше. Исходные принятые решения:
   - Целевые ОС: **Ubuntu 20.04/22.04/24.04/26.04 LTS и Debian 11/12/13**; **без Docker** (пакет OpenVPN, `ck-server`, сервисы systemd).
   - Параметры SSH (хост, порт, пользователь, ключ/пароль/ssh-agent) **настраиваемые, ничего не зашито**. Приложение не должно менять конфигурацию/порт SSH и не может «запирать» пользователя на сервере.
   - Пользователь = сертификат OpenVPN + UID Cloak: создание, отзыв, лимиты (срок/трафик/скорость), выгрузка клиентского пакета.
   - Статус, обновление, удаление, резервные копии конфигов перед изменениями; сначала аудит (только чтение), потом изменения.
   - У пользователя нет доступа к консоли боевых серверов (AWS Lightsail, firewall только TCP 443 и SSH). Разрабатывать и тестировать **только на отдельном тестовом VPS** со снапшотами; боевые серверы не трогать.
   - **Уточнение (2026-10-06):** боевые серверы пользователя — 5 VM Ubuntu 24.04 на AWS Lightsail в разных регионах; доступа к AWS-консоли нет вообще, только **SSH на порту 8081** (это частный случай пользователя — в приложении SSH-порт и все параметры настраиваемые, дефолт 22). Внешний firewall Lightsail изменить нельзя — на ЭТИХ серверах схема должна умещаться в уже открытые порты (SSH 8081 + TCP 443 для Cloak).
   - Тестовое окружение: сначала локальная VM Ubuntu 24.04 (Hyper-V/VirtualBox, снапшоты); WSL2 не подходит (непредставительный systemd/сетевой стек). Для финальной end-to-end проверки — отдельный дешёвый VPS с панелью (снапшоты, переустановка).
   - Перед кодом приложения — эталонное ручное развёртывание OpenVPN+Cloak на тестовой VM с документированием точного рецепта (это спецификация для кода): чек-лист `docs/server-setup.md`. Свериться с актуальными доками Cloak и OpenVPN, а не с памятью.
   - **Управление юзерами Cloak — через admin-API, без SSH** (проверено по cbeuw/Cloak и cbeuw/Cloak-panel): на машине админа `ck-client -a <AdminUID>` поднимает локальный HTTP-эндпоинт; `GET/POST/DELETE /admin/users[/<uid-b64url>]` — список/создание (лимиты: SessionsCap, UpRate, DownRate, UpCredit, DownCredit, ExpiryTime)/удаление. UID — 16 байт base64. Юзеры с лимитами живут в `userinfo.db` (DatabasePath); `BypassUID` в ckserver.json — безлимитные (требует рестарта, основным механизмом не делать). SSH нужен для установки, PKI/CRL и статуса.
   - Перед реализацией сверяться с актуальной документацией Cloak и OpenVPN, а не с памятью.
4. **Локализация:** клиент и админка переведены (см. разделы выше). Остаётся при желании — перевод вывода серверных скриптов `scripts/*.sh` (сейчас их строки идут в лог как есть).
